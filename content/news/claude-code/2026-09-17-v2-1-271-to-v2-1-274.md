Claude Code **v2.1.271** introduced tighter controls for unattended automation. **v2.1.272** contains only the upstream note “Bug fixes and reliability improvements,” so there is nothing more specific to infer from it. **v2.1.273** focused on permission boundaries, managed policy, Remote Control, and long-running sessions. **v2.1.274**, released on September 17, goes further on MCP startup and protocol handling, observability, memory pressure, and recovery from damaged session state.

## v2.1.271: narrower automation controls

The useful automation changes in v2.1.271 remain the same:

- plugin install/update can approve one reviewed marketplace command by SHA-256 rather than granting blanket command approval;
- focused subagents can use `omitClaudeMd: true` to skip ordinary user, project, and local CLAUDE.md files while managed policy still loads;
- sandboxed commands can receive per-command `allowed_domains`;
- Remote sessions can use fast mode subject to plan and organization policy;
- self-hosted runners gained clearer drain and host-configuration controls.

For CI and fleet automation, these controls reduce the amount of trust that has to be granted globally. Digest-bound approval is still approval of code, not a substitute for reviewing the plugin or command itself.

## v2.1.273: policy correctness and long-running sessions

v2.1.273 added opt-in LLM-gateway hint headers through `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` and let a Remote Control session be forked from the Claude app, with the fork continuing as a background session on the machine that owns the original session.

More importantly for managed environments, it fixed cases where Bash permission analysis could skip a prompt, where MDM or `managed-settings.json` MCP restrictions could be ignored alongside server-managed settings, and where a configured memory directory outside the working-directory boundary could still be loaded. It also repaired background/subagent final-output loss, `stream-json` output gaps, context-meter double counting, copied scheduled-task state running in the wrong worktree, and several authentication diagnostics.

## v2.1.274: MCP startup and protocol handling get stronger

The biggest operational changes in v2.1.274 are around MCP:

- `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` can bound how long the first non-interactive turn waits for MCP servers; `0` disables that wait. This is currently release-note functionality rather than a stable environment-variable reference entry, so it is not in the cheatsheet yet.
- HTTP MCP servers that only support legacy HTTP+SSE can recover when the initial Streamable HTTP request returns a 4xx response.
- Streamable HTTP MCP calls now respect a longer per-server timeout instead of failing after roughly five minutes.
- prompts and resources refresh on list-changed notifications even when a server did not declare `listChanged`.
- 403 `insufficient_scope` failures now identify missing permissions and point to `/mcp` re-authentication instead of looking like an expired sign-in.
- `--strict-mcp-config` with an empty `--mcp-config` no longer holds the first non-interactive turn on incidental MCP servers.

The reference documentation now also describes the newer MCP runtime and protocol controls. `MCP_SDK_GENERATION` can pin the MCP client runtime to `v1` or `v2`, and `MCP_PROTOCOL_NEGOTIATION` controls probing for MCP protocol revision 2026-07-28. In v2.1.274 the v2 runtime/default negotiation expands to direct HTTP MCP servers in Bedrock, Claude Platform on AWS, Google Cloud Agent Platform, Microsoft Foundry, Claude apps gateway, and telemetry/feature-flag-disabled installs, subject to host management and Anthropic feature flags. Those independently documented controls have been added to the cheatsheet.

## Better observability and recovery

v2.1.274 also adds the applied `effort` level to the `claude_code.llm_request` OpenTelemetry span. That attribute is independently documented in the monitoring reference and is now reflected in the cheatsheet. The release also introduces a `claude_code.managed_settings_resolved` event with optional redacted settings/digests through `OTEL_LOG_MANAGED_SETTINGS=1`; because that variable is not yet present in the environment-variable reference, it remains article-only for now.

Several reliability fixes are particularly relevant to long-running or headless work:

- corrupted transcripts that loop on `unexpected tool_use_id` can self-heal where possible, otherwise ending with a clear `/rewind` path;
- `/goal` sessions compact and resume more reliably;
- self-hosted runners keep retrying token refresh and recover after a 401;
- resumed non-interactive sessions report unfinished background work correctly;
- background commands are no longer stopped merely because the machine is under mild memory pressure—they are stopped only when memory is critically low;
- Bash permission checks reject or prompt for additional shell-expansion cases that were previously unsafe or ambiguous.

There are also smaller but useful changes for code review, plugins, cloud sessions, and VS Code. For example, `/code-review` uses leaner inline review prompts for models without tuned review settings, plugin clones no longer automatically download Git LFS objects, and VS Code gains continuation after an interrupted window reload.

## What to do

If you rely on MCP, self-hosted runners, background agents, Remote Control, managed policy, or long-running non-interactive sessions, **v2.1.274 is the version to target**:

```bash
claude update
claude --version
```

For production automation, review the MCP runtime/protocol behavior before rollout if you depend on a legacy server or provider-specific gateway. If you need to hold the previous MCP behavior temporarily, use the documented `MCP_SDK_GENERATION=v1` or `MCP_PROTOCOL_NEGOTIATION=legacy` controls while you validate the server side.
