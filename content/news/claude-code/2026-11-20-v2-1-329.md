Claude Code **v2.1.329** and **v2.1.330**, released November 19 and 20, form a useful operations-focused pair. They make trust and managed-hook behavior easier to inspect, give long-running sessions a more complete task view, add enterprise and self-hosted workflow controls, and fix several cases where settings, authentication, MCP connections, Code Mode, or runners could behave unreliably.

## Trust and managed hooks are easier to audit

The trust dialog now says where a folder's hooks are declared. That gives reviewers a concrete place to inspect before allowing project behavior, rather than treating a trust prompt as a generic yes-or-no gate. Claude Desktop and other non-interactive hosts also warn when managed settings hooks fail to load. The warning does not make the hook safe or repair the policy; it makes a missing control visible so an operator can investigate the settings source and the failure.

## `/tasks` becomes the session control surface

`/tasks` now includes this session's scheduled tasks, `/loop` wakeups, the current goal, and conversation forks, alongside shells, monitors, MCP calls, agents, and workflows. The expanded view is useful when a session has several kinds of background work: it lets an operator see what is still active before closing or resuming a session. Exiting can now stop that session's scheduled tasks, except when Claude is still responding, so review the task list before assuming a later resume will be idle.

## MCP and marketplace diagnostics move closer to the failure

The `/mcp` server page adds a Server message row for the JSON-RPC error returned when a remote HTTP MCP server refuses a connection. `/status` also identifies managed marketplaces that do not receive automatic updates and explains why. These changes shorten the path from “an integration is missing” to the server or marketplace condition that needs correction. They do not replace reviewing server credentials, endpoints, plugin code, or managed policy.

## Reliability fixes for settings, identity, and automation

Claude Code no longer resets `~/.claude.json` to defaults merely because a network stall or file lock made it temporarily unreadable during a save. On macOS, a session that can read but cannot write to the Keychain now stops at expiry and explains the problem instead of repeatedly signing out other sessions. The release also fixes `/terminal-setup` around commented or malformed VS Code settings, IDE diff saves that lost a final newline or byte-order mark, and background MCP reconnects that stalled on an older protocol version.

Code Mode receives several memory and lifecycle fixes, including limits for runaway loops, bounded reads of very large line ranges, and cleanup of large text retained across background-agent wakeups. Self-hosted runners gain safer Git LFS startup behavior and fixes for repository paths, remote MCP reconnects, and session startup status. These are reasons to upgrade a canary, not reasons to remove existing permission, hook, or runner review.

## v2.1.330 adds enterprise and runner controls

The next release adds sign-in to organizations managed in Anthropic's Enterprise Admin Console. After `claude auth login`, Claude Code can apply the organization's settings and use its configured cloud provider or gateway. That matters for teams whose authentication and routing policy is managed centrally: the login step becomes part of the organization's control plane rather than a purely local setup.

On macOS and Linux, the built-in `easel` mod can draw charts when requested and under MCP metrics results for supported Pro, Max, Team, and Enterprise accounts. Automatic charts can be turned off in `/config`. Treat the chart output as a presentation aid, not as a new data authority; the underlying MCP metrics and their permissions still deserve review.

Two smaller controls address operational edge cases. Setting `CLAUDE_CODE_FULL_SIGN_IN_LINK=1` prints the complete sign-in link when the shortened link produces an error or a script needs to read it. Self-hosted runners add `--start-dir` and `SELF_HOSTED_RUNNER_START_DIR`, which let Claude begin work in a repository subfolder while keeping settings and hooks loaded as before. The release also adds clearer notices when runner sessions cannot fetch a plugin marketplace or when managed Git rejects a plugin's own repository.

## What to do

Upgrade a canary installation and inspect the new diagnostics in a disposable project:

```bash
claude update
claude --version
```

Before trusting project hooks, check the declared settings source and review the hook files. If you operate long-lived or self-hosted sessions, use `/tasks`, `/status`, and `/mcp` during a controlled reconnect test. For centrally managed organizations, verify the post-login provider and settings. For runners that use a repository subfolder, test `--start-dir` with a non-destructive task before changing the default. Keep this article as a draft until the exact workflows and terminology have been reviewed.
