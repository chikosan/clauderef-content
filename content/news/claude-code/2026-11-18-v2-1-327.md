Claude Code **v2.1.327**, released November 17, is a practical safety and observability update. It adds confirmation around a repository-changing setup flow, gives MCP users a safer way to pass JSON configuration, and makes several kinds of degraded configuration visible from the terminal. It also fixes two failure modes that could delete files or directories in unattended environments.

## Safer setup and safer secrets

The `/install-github-app` flow now asks for confirmation before it changes a repository. The command can install the Claude GitHub App, save an authentication secret, create workflow files, push a branch, and prepare a pull request. Confirmation does not replace reviewing the resulting permissions or workflow, but it adds an explicit pause before a command with repository-wide effects.

MCP configuration gets a useful shell-safety improvement too. `claude mcp add-json <name> -` reads the server's JSON from standard input. That makes it possible to source a secret-bearing configuration without placing the JSON directly in the command line, where it may be exposed in shell history or process listings. This stdin form is a CLI feature; the release notes say it is not available from inside a Claude Code session.

For example, a wrapper can keep the configuration in a protected file and pipe it to Claude Code:

```bash
umask 077
claude mcp add-json my-server - < ./mcp-server.json
```

The safer transport does not make the server trustworthy. Review the command, endpoint, credentials, and scope before adding it, and avoid printing the JSON in diagnostics.

## `/status` becomes a configuration check

The release expands `/status` into a more useful first stop when a capability is missing or behaving differently than expected. It can list broken agent, skill, command, and output-style files; keybinding errors; an unavailable sandbox; permission settings that were ignored; and hook matchers that never match. `/config` also now notes when another settings source overrides a row, which is important because user, project, managed, command-line, and environment settings have different precedence.

These messages change the debugging sequence. Before reinstalling a plugin or broadening permissions, inspect the status and configuration notices, then fix the smallest broken input. The MCP documentation likewise recommends checking server status and configuration warnings when a server fails to load.

## Important fixes for unattended environments

Two fixes deserve special attention for remote and self-hosted use. Stopping a Remote Control server in worktree mode no longer deletes running sessions' git-ignored files, such as `.env`. Self-hosted runners started with `--use-anthropic-git-proxy` no longer delete a non-empty directory named by `GIT_CONFIG_GLOBAL`; they keep the directory, ignore the variable, and warn instead.

The changelog also records safer MCP project-scope edits, confirmation before `/export` overwrites an existing file, better recovery for resumed and background sessions, and fixes for several plugin, permissions, proxy, and settings-save edge cases. Those are mostly reliability corrections, but they reinforce the same operational rule: upgrade a canary first, keep backups for unattended worktrees, and treat new warnings as information to investigate rather than prompts to disable safeguards.

## What to do

Upgrade a canary installation, test the GitHub App setup in a disposable repository, move sensitive MCP JSON to stdin where appropriate, and use `/status` when a project behaves differently from its settings. Keep the article draft until a maintainer reviews the exact workflow and local policy implications.
