Claude Code **v2.1.332**, released November 25, adds two useful control points for extensibility: MCP servers can provide skills, and a new hook can block shell commands injected as a skill loads. The release also includes practical reliability fixes for authentication, named pipes, MCP connections, compaction, hooks, and long sessions.

## Skills can come from MCP servers

MCP servers can now provide skills alongside their tools. In the terminal, these skills appear in the `/` menu with a `server:skill` name, while ordinary local and plugin skills keep their existing names. Claude reads supporting files from the MCP server as MCP resources, so a server can package a reusable workflow instead of exposing every instruction as a tool description.

This is beta functionality and has an important trust boundary: the skill content comes from the server. Claude Code's MCP documentation describes per-server permission rules that can block the server's skills, ask before loading them, or skip the prompt. Treat a new MCP skill like installable agent code—review its instructions, supporting resources, commands, and network behavior before allowing it in a project.

## A hook can stop injected shell commands

Skills can inject dynamic context by running inline shell commands as they load. Before this release, `PreToolUse` did not see those injected commands. `PreSkillShellCommand` fills that gap: a command hook can inspect the command and block it, either by exiting with status 2 or returning a deny decision. It cannot approve or rewrite the command.

The event covers `Bash` and `PowerShell` commands that passed the skill-load permission check, including commands run in bypass-permissions mode. In auto mode, commands that still need approval do not run during skill loading; if Claude later calls the command as a normal tool, `PreToolUse` is the event that sees it. Teams that need coverage in both paths should configure both hooks.

The version requirement matters. The official hook reference says `PreSkillShellCommand` requires Claude Code v2.1.332 or later. On v2.1.331 and older, putting the event in settings produces an unknown-hook warning and the command is not protected by this hook. Roll out the client update first, then add the setting and test it with a harmless fixture.

## Reliability fixes worth upgrading for

The release fixes reads, `@` mentions, and compaction hanging on named pipes that have no writer; those operations now fail after 20 seconds. It also fixes several MCP failure modes, including an SSE server that comes back on a different endpoint and a local server that floods standard output. These are operationally meaningful because a stalled tool or file read can otherwise look like a frozen agent session.

There are additional safeguards for hooks and long sessions: runaway hook output is shortened, hook failures with huge logs are less likely to freeze or overflow context, and several resume, compaction, model-selection, and background-session paths were repaired. Authentication now reports failure when `claude auth login` cannot save the login instead of printing a misleading success message.

## What to do

Upgrade a canary installation, then verify the new control path before enabling it broadly:

```bash
claude update
claude --version
claude doctor
```

For MCP administrators, start with a server-level permission rule and inspect each provided skill before allowing it. For teams that use dynamic skill context, add a `PreSkillShellCommand` policy only after every supported terminal, desktop, and IDE client has reached v2.1.332 or later. Keep `PreToolUse` coverage for commands Claude invokes after the skill has loaded.
