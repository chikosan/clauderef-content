Claude Code **v2.1.325** is primarily a hardening release. It changes the default interaction between sandboxed Bash and permission prompts, fixes several ways that permissions or account boundaries could be applied incorrectly, and improves behavior for teams using MCP, subagents, third-party gateways, and scheduled work. The [official release notes](https://github.com/anthropics/claude-code/releases/tag/v2.1.325) contain a long list of fixes, so this summary focuses on changes that can alter an operating policy or deserve a regression check.

## Sandboxed Bash now asks by default

When Bash runs inside the sandbox, Claude Code now follows the normal permission flow by default. The release notes identify `sandbox.autoAllowBashIfSandboxed: true` as the opt-in setting that preserves automatic execution for sandboxed Bash. Managed settings that enable the sandbox need the same setting in the highest-ranking managed source if an organization wants commands to run without prompts.

That is a meaningful change for unattended workflows. A sandbox limits what a command can reach, but it does not make every command harmless: a command can still alter the project, consume resources, or produce an unexpected result. Start by testing the prompts your team expects, then decide whether the narrower auto-allow behavior is appropriate for a controlled environment. Record the setting explicitly rather than relying on an older default.

## Permission and sandbox boundaries get more checks

Version 2.1.325 fixes additional cases involving Bash permission rules, compound commands, protected files, relative paths, worktrees, and sandbox writes. It also closes paths where a linked worktree or repository settings could be treated as more trusted than intended. These changes are useful security maintenance, but they can expose assumptions in an allowlist that was written against older parsing or directory behavior.

The practical response is to retest representative commands, not to broaden permissions when a prompt appears. Include commands wrapped in shells or utilities, operations from a linked worktree, writes under `.claude`, and any rule that uses a relative path. Keep the test repository disposable and inspect the resulting permission decision before changing a shared policy.

## Account and integration boundaries are clearer

The release fixes more background-session cases where credentials from the launching shell, a different profile, or another sign-in could be used unexpectedly. It also improves behavior around MCP reconnection, OAuth questions in headless mode, plugin reloads, connector approvals, and artifact access. Teams that run background sessions or authenticated MCP servers should check both the account identity and the server connection after upgrading.

Several fixes affect hosted or alternate model paths: third-party gateways and Foundry can avoid a premature context-length failure, subagents keep their requested model instead of inheriting an unrelated plan-mode model, and model-specific reads and MCP results use the subagent’s model sizing. These are operational corrections rather than a performance guarantee, so compare a known workflow before and after the update.

## What to do

Upgrade a canary installation, confirm its version, then exercise a permission-heavy task, a background session, an authenticated MCP server, and a subagent with an explicit model. If your organization intentionally relies on prompt-free sandboxed Bash, review the managed setting before rollout:

```bash
claude update
claude --version
```

Keep the old policy available for comparison, but do not weaken a new prompt simply to make a test pass. Read the [full Claude Code v2.1.325 release notes](https://github.com/anthropics/claude-code/releases/tag/v2.1.325) and the [settings reference](https://code.claude.com/docs/en/settings) for the exact precedence and configuration syntax.
