Claude Code **v2.1.326** is a diagnostics and reliability release for teams, managed environments, and long-running sessions. The most visible change is that Code Mode can now run while agent teams are enabled. The release also makes hidden configuration decisions easier to explain, adds an opt-in telemetry setting, and fixes a wide set of safety and recovery edge cases.

## Code Mode now works with agent teams

If Code Mode is already enabled, sessions that use agent teams now start in Code Mode too. This removes a confusing split where a team session could otherwise fall back to a different tool-calling mode. It does not make Code Mode appropriate for every repository: treat the combination as a workflow change, compare the generated tool calls with a normal session, and keep the same permission and review boundaries.

The release also fixes skills, slash commands, and background subagents that could fail in Code Mode when an inline `!` command needed approval. Mods can now use Bash, Read, and other tools through `$.tool.call` and `$.tool.check` more reliably. These are useful corrections for plugin and mod authors, but they are not a reason to grant broader permissions automatically.

## Status and startup messages explain more

`/status` now includes a row explaining when a provider or an environment variable such as `DISABLE_TELEMETRY` turns features off. Claude Code also warns when an `--allowedTools`, `--disallowedTools`, or `--tools` value does not look like a complete rule, and explains why MCP servers stop loading if an administrator adds `managed-mcp.json` during a session.

Plugin users get similar feedback: `/plugin` and `claude plugin list` now say when a malformed `plugin.json` field, such as `author` or `homepage`, was ignored. Ctrl+O can reveal hidden startup notices, and the empty prompt now offers a next step after a request fails. Together these changes make a failed or degraded session easier to diagnose before changing policy or reinstalling an integration.

## Host identity in telemetry is opt-in

`OTEL_RESOURCE_INCLUDE_HOST` can include `host.name` and `host.id` in OpenTelemetry resource attributes. It is off by default. Enable it only when the operational value of host-level correlation outweighs the privacy and retention implications for your telemetry backend. Host identity can be sensitive in shared, ephemeral, or customer-facing environments, so apply the same access controls and redaction policy used for other infrastructure metadata.

The release also fixes missing OpenTelemetry `tool_decision` and `permission_denials` entries when managed PreToolUse hooks refuse a direct tool call. That improves observability for policy debugging, but telemetry should not be treated as a permission boundary: keep the actual managed settings and hook behavior under review.

## Safer behavior across settings, MCP, and sessions

Claude Code now warns when settings cannot be written instead of making a permission rule or `/add-dir` folder appear saved. Settings values nested beyond 64 levels are dropped with a warning rather than crashing or partially applying. Bash commands that delete or overwrite files are also classified more accurately in the transcript, while a misleading dangerous-`rm` warning is reduced in cases where the command cannot be read reliably.

MCP fixes cover failed `headersHelper` scripts, nearly identical server names, schema branches using `anyOf` or `oneOf`, reconnecting to servers removed by an SDK host, and clearer local stdio failure messages. Background services stop rather than sending a request through a missing shell gateway, and they are less likely to terminate an unrelated process after a process number is reused. Remote Control and cloud-session file handling also avoid overwriting a changed copy in one Linux path.

## What to do

Upgrade a canary and test one agent-team session with Code Mode, one managed settings failure, one MCP reconnect or authentication flow, and one background session. If you operate OpenTelemetry, decide explicitly whether host identity is acceptable in your backend before enabling the new variable:

```bash
claude update
claude --version
```

Do not broaden permissions just to silence a new diagnostic. First identify which setting, provider, plugin field, MCP server, or session boundary produced the message, then make the smallest reviewed change.
