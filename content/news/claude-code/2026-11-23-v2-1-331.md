Claude Code **v2.1.331**, released November 23, is a practical operations release. It adds clearer connectivity evidence, expands where terminal Code Mode can run, exposes a narrowly targeted response-compression switch, and gives plugin authors a way to separate optional components from the core install. The release also contains a large set of reliability fixes, including a serious-looking class of MCP hangs and several long-session recovery paths.

## Connectivity failures are easier to classify

`claude doctor` now includes an API connectivity section. When the check runs, it reports whether the API could be reached, includes the HTTP status when there is one, or shows the error that prevented the connection. If the check was not performed, it explains why instead of presenting an ambiguous healthy-looking result.

That makes `claude doctor` more useful as the first capture in a support or deployment investigation. It does not prove that every model request, gateway policy, proxy route, or MCP server will work; it identifies whether the basic API path was tested and what happened at that boundary.

## Code Mode reaches more terminal sessions

This version adds Code Mode support in terminal sessions on Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, and Claude Platform on AWS. The availability is provider- and account-dependent, so treat this as a compatibility expansion rather than a promise that every existing gateway configuration can use it immediately.

The release also fixes resumed Code Mode sessions that could lose thinking and prompt-cache state when `--resume` or `--continue` was used with another permission mode. It improves tool search descriptions and ensures `--bare` sessions are told what their scripts can call. Those details matter when a team moves from a local test session to a managed or resumed workflow: verify the effective permission mode and available tools instead of assuming the resumed session inherited everything.

## A targeted escape hatch for compressed responses

`CLAUDE_CODE_DISABLE_RESPONSE_COMPRESSION` asks Claude Code to request uncompressed model responses. The release notes position it for proxies that cut off compressed responses and explicitly do not yet recommend it for self-hosted runners or Remote Control. Use it as a diagnostic or compatibility switch for a known proxy failure, not as a default hardening setting.

The same release adds `CLAUDE_GATEWAY_IDP_CONNECT_BY_HOSTNAME=1` for Claude apps gateways using `oidc.use_proxy: true`, and adds more `gen_ai.*` fields to `claude_code.llm_request` trace spans. The telemetry additions include input-token usage with prompt-cache tokens, which can make traces more useful for cost and latency analysis when the surrounding collector is configured to accept them.

## Plugins and MCP get safer failure modes

Plugin manifests can now declare `optionalDependencies`. A plugin can list components that may be installed, disabled, or uninstalled independently, making a partial feature set explicit instead of treating every add-on as inseparable from the base plugin.

Claude Code also fixes MCP tool calls hanging for up to 30 minutes after some malformed replies from local or WebSocket servers. That is a reason to upgrade before diagnosing a slow tool as an application-level timeout. It is not a reason to stop validating server responses, permissions, or reconnect behavior: a malformed reply still indicates a server-side compatibility problem.

## What to do

Upgrade a canary installation and capture the new diagnostic output:

```bash
claude update
claude --version
claude doctor
```

If a proxy is known to truncate compressed responses, test `CLAUDE_CODE_DISABLE_RESPONSE_COMPRESSION` in an isolated session and record whether the failure changes. If you run terminal Code Mode through a cloud provider, verify the provider's supported configuration and permission behavior. For plugin and MCP maintainers, test optional dependency lifecycle and malformed-reply handling before rolling the release across a fleet.
